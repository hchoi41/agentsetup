# Google Sheets: landing raw data with Connected Sheets

This file covers step P2 of the procedure in [SKILL.md](../SKILL.md) for Google Sheets: how a BigQuery SQL result reaches a raw sheet through Connected Sheets, what a refresh does, what differs from Excel, and how a model moves between the two products. Read it before you give a user Connected Sheets steps, before you claim that a workbook works in Google Sheets, and when a user keeps a model in Google Sheets.

The skill's rule comes first: the SQL shapes the data to the agreed column contract and lands it on the raw sheet; every analysis step after that is a workbook formula (Max, spec 1.2; [column-contract.md](column-contract.md)).

Nothing in this file was tested in Google Sheets. The builders of this plugin had no Google account access, so no workbook was opened in Google Sheets and no Connected Sheets query was run (spec 2.7). Every statement about Google's products below comes from Google's published pages, as the research read them.

- "design n": section n of the plugin's design (`rotm_design_v1.md`, kept in the project's build folder, not shipped). It describes what the plugin does.
- "Max, spec 1.x": Max's own words, quoted from Part 1 of the job's specification.
- The research files are kept in the project folder and are not shipped with the plugin. The section [Sources](#sources) at the end of this file gives, for each research identifier this file cites, the publisher, the page title, the link and the date the research read the page.

## What Connected Sheets puts on a grid

- Connected Sheets has five object types: the data source sheet (a preview), the extract, the pivot table, the chart and the function. Calculated columns are defined on the data source and cannot be placed on a grid by themselves (platforms A1.1, not confirmed).
- The data source sheet shows a preview of only 500 rows (researcher 2 #15, confirmed). Pivot tables, functions and charts on the data source use the full data (platforms A1.2, not confirmed).
- An extract "imports a static dump of data from the data source into Sheets" and is anchored at its top-left cell (platforms A1.3, not confirmed). Its definition lives in the anchor cell, and its size is computed from its settings (platforms A1.4, not confirmed).
- Extracts let ordinary functions read their values and ranges (platforms A1.5, not confirmed). The research reads this as: the extract is the only object that puts plain values on a grid where A1 formulas can read them. The skill therefore lands every raw table as an extract.
- "You can't change BigQuery data from within Google Sheets." The extract's columns, filters, sort and row limit are set in the extract editor (platforms A1.15, not confirmed).

## Limits

- An extract holds up to 500,000 rows or 10 MB. At 50,000 rows or fewer there is no cell limit. From 50,001 to 500,000 rows it holds at most 5 million cells (platforms A1.6, confirmed; researcher 2 #15, confirmed).
- Above 500,000 rows, Google's BigQuery page says the data pull is not supported, and the Docs help page says only the first 500,000 rows appear (platforms A1.6, confirmed). So compare the landed row count with the contract after every refresh: the generated check `<t>_rows` does this ([checks.md](checks.md)).
- A spreadsheet created in or converted to Google Sheets holds up to 20 million cells or 100 MB (researcher 2 #16, confirmed). The limit is for the whole spreadsheet, so helper sheets count toward it: a helper sheet of 100,000 rows and 20 columns uses 2,000,000 cells.
- When an Excel file is converted, every cell with more than 50,000 characters is removed (researcher 2 #16, confirmed).

## SQL and parameters

- The path for custom SQL: Data > Data connectors > Connect to BigQuery > choose the project > Saved queries and query editor; enter the query; click Insert results. Only GoogleSQL (BigQuery's standard SQL) works with this connector (platforms A1.9, not confirmed).
- `rotm.py land` writes `queries/<t>.sql` in GoogleSQL: `SELECT <source_expression> AS <name>, ... FROM <source.from> WHERE <source.where> ORDER BY <key>`, one SELECT item per contract column in contract order (design 7.4). You may edit the file after the contract is agreed; keep the column names and their order.
- A parameter is written `@NAME` in the query and mapped to a cell in the query editor's Parameters panel, for example `WHERE state_name = @STATENAME`. A list parameter needs `UNNEST()`, and a type mismatch can be fixed with `CAST` (platforms A1.10, not confirmed). Since 11 August 2026 a list parameter can take a range in which each cell is one item (platforms A1.11, not confirmed). In a model built by the plugin, a parameter cell belongs on the `inputs` sheet.
- To change a saved query, edit it in BigQuery. The change appears in Connected Sheets within 5 minutes; Sync from BigQuery, then Connect, picks it up (platforms A1.16, not confirmed).

## Landing a raw table: the steps

Give these steps to the user; the plugin cannot run the steps in BigQuery and Google Sheets. `rotm.py land` without `--csv` prints steps 6 to 9 in one note for a Connected Sheets table (design 7.4).

1. Agree the contract for the table ([column-contract.md](column-contract.md)) and run `rotm.py land MODEL --table <t>` to write `queries/<t>.sql`.
2. The first extract (not tested in Google Sheets or BigQuery: the builders ran no SQL against BigQuery). The user runs the SQL of `queries/<t>.sql` in BigQuery, or takes a staging extract of the same query, and exports the result as a CSV file with the header row in the contract's column order. Ask the user for the row count and the control total that the source reports for the same query.
3. `rotm.py land MODEL --table <t> --csv <file>` checks the CSV against the contract (column names and order, types, nulls, allowed values, key, row count and control totals) and writes `raw/<t>.csv`. A CSV it refuses writes nothing: report each refusal line to the user and stop ([SKILL.md](../SKILL.md), P2). A row count or a control total of the source that differs from the contract's is a contract change: propose it, show it and get it agreed again.
4. Only then build the workbook as `.xlsx` with `rotm.py build MODEL`. Build reads `raw/<t>.csv` and writes it to `raw_<t>` as a static snapshot. The static snapshot stands in for the extract until the cutover (step 8 and [Cutover when the extract is on a new sheet](#cutover-when-the-extract-is-on-a-new-sheet)): until then every number the model shows comes from `raw/<t>.csv`, not from the extract.
5. Convert the workbook in Google Drive to a Google Sheets file. Google Sheets converts `.xls` and `.xlsx` files (platforms A4.1, not confirmed).
6. In the converted file: Data > Data connectors > Connect to BigQuery > the project > Saved queries and query editor. Paste the SQL from `queries/<t>.sql`. Click Insert results (platforms A1.9, not confirmed).
7. Create an extract with every column of the query, in the contract's order (platforms A1.3 and A1.15, not confirmed).
8. Place the extract on the sheet `raw_<t>` at A1, with nothing else on the sheet (design 7.1, D9). Whether an extract can be placed on a sheet that already exists, and whether it writes its header in the anchor row, is not confirmed (research synthesis section 5). If the extract lands on a new sheet, the model's formulas still read the static snapshot on `raw_<t>`: do the steps in [Cutover when the extract is on a new sheet](#cutover-when-the-extract-is-on-a-new-sheet) before you report any result.
9. Refresh with More > Refresh options: one object, everything on one data source, or everything on all data sources ("Refresh all"). A refresh updates the extracts, pivot tables, charts and functions linked to the data. BigQuery data does not sync by itself (platforms A1.13, not confirmed).
10. To audit or check the model, download it with File > Download > Microsoft Excel (.xlsx) and follow [Models kept in Google Sheets](#models-kept-in-google-sheets): `rotm.py audit` runs on the download by itself; `rotm.py check` needs the download saved in a copy of the model folder (research synthesis D25, a recommendation; not tested in Google Sheets).

## Cutover when the extract is on a new sheet

These steps are not tested: the builders had no Google account, and how Connected Sheets anchors, moves and names an extract is not confirmed (research synthesis section 5). The model reads a raw table only from the sheet `raw_<t>`: the helper columns read `=INDEX(raw_<t>!$X:$X,A2)` and the checks read whole columns of `raw_<t>`. An extract on any other sheet is not read by the model.

1. Make `raw_<t>` the sheet that holds the extract, with the extract's header in row 1 and its first data row in row 2. There are two ways:
   - Remove the static snapshot's contents from `raw_<t>`: select every cell of the sheet and delete the contents. Keep the sheet itself, so that the formulas that name it stay as they are. Then place the extract at A1 of `raw_<t>`.
   - Rename the sheets: give the static sheet another name, then give the extract's sheet the name `raw_<t>`. Excel changes the formulas that name a sheet when the sheet is renamed; whether Google Sheets does the same is not confirmed. If it does, the formulas follow the static sheet to its new name and still read the static snapshot, with no error. Step 3 shows which sheet the formulas read.
2. If neither way gives `raw_<t>` the extract with its header in row 1, change the raw sheet's name in the specification, build again and convert again. The specification schema accepts only `raw_<table>` as the name of a raw sheet, so a new sheet name means a new table name: propose and agree the contract for that table name ([column-contract.md](column-contract.md)), land the first extract for that table name (steps 2 and 3 of [Landing a raw table: the steps](#landing-a-raw-table-the-steps)), change the raw sheet's `table` and `name` and every placeholder that names the table in `model.spec.json`, run `rotm.py build`, convert the new `.xlsx` (step 5), and place the extract again (steps 6 to 8).
3. Find out which sheet the formulas read before you report any result. A matching header, row count and control total do not show it: at the first cutover the extract holds the same rows as the static snapshot, so these comparisons agree whichever sheet the formulas read.
   - The proof is the sheet named in two formulas: the first fetch cell on `h_<t>` (row 2 of the first fetch column, column C in a model the plugin built, for example `=INDEX(raw_<t>!$A:$A,A2)&""`), and the Actual cell (column D) of the check `<t>_rows` on the checks sheet. Both must name the sheet that holds the extract.
   - Add a row-level comparison at the first refresh that changes rows: choose one key, or one group (for example one region and month), whose value changed in the source, and compare the value the model shows for it with the value the source system reports. If the model still shows the old value, it reads the static snapshot.
   - Compare the extract with the contract and the source as well; these comparisons test the data, not the cutover. The header: the column names in row 1 of `raw_<t>`, in order, equal the contract's columns. The row count: the rows the check `<t>_rows` counts equal the row count the source reports for the query, and lie within the contract's expected rows. The control total: the total the check `<t>_total_<column>` reads equals the total the source system reports for the same query (the contract's control total belongs to the snapshot landed before; after a refresh, ask the user for the source's current total).
4. If neither the formula reading nor the row-level comparison can be done, or either one points at the static sheet or the old value, the report says that the model still reads the static snapshot landed in `raw/<t>.csv`, not the extract, and it reports no number as computed from the refreshed data.

## Scheduled refresh

- A scheduled refresh updates all objects at a preset time and runs as the user who set it up (platforms A1.14, confirmed).
- When another user adds or updates a data source, the schedule pauses until someone takes it over (platforms A1.14, confirmed).
- Objects in the preview or failed state do not refresh with a scheduled refresh (platforms A1.14, confirmed).
- Users with Sheets-only access cannot refresh or schedule a refresh (platforms A1.14, confirmed).

## What a refresh does to the formulas that read an extract

- Not confirmed: what happens to ordinary formulas that point into or below an extract when a refresh changes its row count: whether cells below it shift, are overwritten, or show an error. Google documents only that the extract's size is computed from its settings (platforms E2).
- Not confirmed: whether the cells of an extract can be typed over by hand, and what happens if they are (platforms E1).
- Not confirmed: whether a Connected Sheets calculated column can be included in an extract (platforms E3).
- What the skill does about it (design 7.1, 7.4):
  1. Nothing else is placed on a raw sheet: no formulas, totals, notes or checks, and nothing is typed into it.
  2. Helper columns on `h_<t>` read raw row r by position, `=INDEX(raw_<t>!$X:$X,A2)`, over the whole column. No formula points at one cell of the extract.
  3. Calculation blocks read helper and raw columns as whole columns.
  4. After every refresh, the in-workbook checks `<t>_rows`, `<t>_cover` and `<t>_beyond` turn to 1, and the master check with them, when the row count is outside the contract, when the helper rows do not reach the last raw row, or when helper rows lie below the last raw row. They are plain formulas, so they need no plugin; that they behave the same in Google Sheets is expected and was not tested.
  5. To repair the helper rows in Google Sheets after a refresh, use the procedure for the direction of the change. The three procedures are not tested in Google Sheets. They do by hand what `rotm.py extend` does in Excel, and the Excel procedure (`rotm.py extend` after a refresh of an Excel Power Query table) was tested in both directions, to more rows and to fewer rows, and to zero rows and back to one row (tests `test_v2_core.py::test_power_query_raw_table_keeps_its_formats_through_attach_growth_and_shrink` and `test_v3_raw.py::test_empty_table_through_power_query_one_zero_one`, both with Excel).
     - More raw rows than helper rows (`<t>_cover` shows FAIL): copy the last helper row (column A to the last helper column) and paste it down to the last raw row. Every helper formula is position-based, so the copied rows are correct (design 7.2).
     - Fewer raw rows than helper rows (`<t>_beyond` shows FAIL): clear the contents of the helper rows below the last raw row (column A to the last helper column; clear the contents, do not delete the rows), and leave the rows above untouched. A helper row below the last raw row reads empty raw cells as 0 and feeds the calculations until it is cleared ([checks.md](checks.md)).
     - Zero raw rows (the refresh returned the header row only; the check `<t>_rows` holds only when the contract was agreed with `--allow-empty`): before you clear anything, keep a copy of the formulas of helper row 2. Either take them from `model.manifest.json` (the entry of the helper sheet `h_<t>` under `sheets` lists each helper column's letter `col` and its row 2 formula `formula`), or copy them as text onto the notes sheet. Then clear the contents of every helper row, row 2 included. When a later refresh returns rows, write them back into row 2, each formula in its column, and copy row 2 down to the last raw row.
     - After each repair read `<t>_cover`, `<t>_beyond` and the master check (`checks!C2`): each must show OK. If one shows FAIL, the helper rows do not end at the last raw row yet.
     - After the repair for fewer raw rows or for zero raw rows, `rotm.py check --strict` and `rotm.py audit --strict` of the copy of the model folder (step 4 of [Models kept in Google Sheets](#models-kept-in-google-sheets)) pass: the audit reads the helper rows down to the last row of the raw sheet, so the cleared rows below it give no finding, and it reports helper formulas left below that row as H-BEYOND. This was tested here with a local stand-in (a copy of a built workbook changed with openpyxl), not in Google Sheets (tests `test_v6_audit.py::test_shorter_extract_repair_passes_check_and_audit` and `test_v6_audit.py::test_zero_row_repair_passes_check_and_audit`). With Excel, `rotm.py check --strict` of the same stand-in exits 0 with every check holding, and `rotm.py audit --strict` of the workbook Excel saved exits 0 (test `test_v6_integrator.py::test_repaired_download_passes_check_with_excel`).
- Whether whole-column INDEX keeps working after an extract refresh in Google Sheets is not confirmed (design 22). It was tested only over an Excel Power Query table ([excel-power-query.md](excel-power-query.md#the-plugins-layout-over-a-query-table-local-test-2026-11-25)).

| Excel tables on import | the import of Excel tables as Sheets tables is the confirmed announcement of 11 August 2026; the announcement says that pivot tables backed by table ranges import in a gradual rollout (researcher 2 #17, confirmed). Not confirmed, item by item: whether the table styles come through, whether structured references in formulas (such as `Table1[Column]`) keep working after the import, and whether a connected pivot table stays connected to its table (platforms E5, not confirmed) | | the skill does not rely on it: formulas read whole columns, not table names |
| Functions in one product only | QUERY, ARRAYFORMULA and IMPORTRANGE are Google Sheets functions (platforms A3.3, confirmed for this part); that Excel has none of them is not stated by the cited page (not confirmed) | Google lists CALL, the CUBE functions (CUBEKPIMEMBER, CUBEMEMBER, CUBEMEMBERPROPERTY and others), INFO, REGISTER.ID, RTD and WEBSERVICE as not supported in Sheets (researcher 2 #20, confirmed) | refused in profile `both` (F-FUNC-REFUSED); `rotm.py compat` reports or replaces them; the full list is in [functions.md](functions.md) |
| Newer Excel functions | the fetched Google function list did not show SORTBY, TAKE, DROP, TEXTSPLIT, GROUPBY, PIVOTBY or TRIMRANGE; Sheets has SPLIT; XMATCH has a help page although it was missing from the fetched list (platforms A3.5, confirmed as an absence from one fetched copy) | LET is in Microsoft 365, 2024 and 2021; LAMBDA only in Microsoft 365 and 2024 (platforms A3.6, confirmed) | functions whose Sheets availability is not confirmed are flagged; LAMBDA is refused; LET is flagged ([functions.md](functions.md)) |
| Arrays | many array formulas expand into neighbouring cells by themselves (platforms A3.4, not confirmed) | spilled arrays are not supported inside Excel tables; a blocked spill shows `#SPILL!` (platforms A3.7, not confirmed) | spilling functions are flagged (F-FUNC-FLAGGED); helper columns copy one formula down instead |

| Empty cells read by a formula | not confirmed: Sheets is said to return an empty value (research synthesis D5, not in the reports) | INDEX of an empty cell returns 0 (observed by the research synthesis in this PC's Excel 16.0; not confirmed by a claim check) | text fetch columns append `&""`, so an empty text shows as "" in both products (design 7.1) |

## Converting a workbook from Excel to Google Sheets

- Google documents only one conversion loss: cells over 50,000 characters are removed (platforms A4.1, not confirmed; the 50,000-character rule itself: researcher 2 #16, confirmed).
- Not confirmed: how Arial (and Korean text in an Arial cell), fills, number formats including `_)` and `[Red]`, the number formats `date_or_empty` and `datetime_or_empty` (an empty date shown as an empty cell), named cell styles, conditional formats, data validation, defined names, freeze panes, hidden gridlines, and notes or comments come through the conversion (platforms A4.3 and E5, not confirmed). No Google page lists them item by item.
- Excel tables: the import of Excel tables as Sheets tables is the confirmed announcement of 11 August 2026 (researcher 2 #17, confirmed). Not confirmed, item by item: whether the table styles come through, whether structured references in formulas (such as `Table1[Column]`) keep working after the import, and whether a connected pivot table stays connected to its table (platforms E5, not confirmed). The announcement says that pivot tables backed by table ranges import in a gradual rollout (researcher 2 #17, confirmed).
- So after a conversion: say in your report that the workbook was converted but not opened and checked in Google Sheets by the plugin, and ask the user to look at the converted sheets.
- `rotm.py compat <workbook>` reports every function and feature that exists in one product only, and replaces the mechanical cases: `[@Col]` and `#This Row` references with same-row A1 references, `_xlfn.` text where the function exists in both, `CONCATENATE` with `&` (design 15), and a `CONCAT` with one argument or with more than two arguments, each a single value, with `&` (one argument `a` becomes `a&""`; Google Sheets' CONCAT takes two values, so exactly two single values is the form both products share; a CONCAT with a range argument is reported and not replaced). An Excel `FILTER` with a third argument is reported at its cell (`X-FILTER`, a warning) and not rewritten: in Excel the third argument is the value returned when no row matches, in Google Sheets it is a further condition ([functions.md](functions.md)). Afterwards the cross-product audit rules pass for the replaced cells. The same function catalogue is applied to the formulas of data validations and conditional-format rules: a function one product lacks is `X-FUNC` with the sheet, the range and the kind of rule; these formulas are reported, not rewritten. compat checks by rule; it does not open Google Sheets.

## Models kept in Google Sheets

The plugin's scripts read `.xlsx` files. For a model that lives in Google Sheets (research synthesis D25, a recommendation; not tested in Google Sheets: the behaviour of `audit`, `check` and `recalc` below was seen on workbooks built in Excel only):

1. Download it with File > Download > Microsoft Excel (.xlsx). The values in the download were computed by Google Sheets.
2. `rotm.py audit <download>.xlsx` runs on the download by itself, in any folder. Without the model folder it applies the rules that need no manifest: the formula rules (depth, length, functions available in both products), the raw-sheet rules for sheets named `raw_...`, the style palette as a whole, and the check cells it can infer. It reads the values saved in the download, which Google Sheets computed; it does not recalculate.
3. `rotm.py check` needs the model folder: it refuses (exit 2) a workbook with no `rotm_model.json` in its folder or above it, and a workbook with no `model.manifest.json` beside it. So:
   1. Copy the model folder that built the workbook (its `rotm_model.json`, `model.manifest.json` and `model.spec.json`, and its folders `contracts` and `raw`) to a new folder, so that the original folder keeps its own workbook. Do not copy the workbook: the copy of the model folder holds no workbook before the download is saved there. Copy the folders `contracts` and `raw` before `rotm_model.json`: once the marker is in the new folder, the raw-sheet guard refuses every write into its `raw/` folder.
   2. Save the download in the copy under the model's workbook name (the `workbook` field of `rotm_model.json`, `model.xlsx` by default), beside its `model.manifest.json`. With the plugin's hooks on, the raw-sheet guard lets a copy to a new workbook name in a model folder through, and refuses a copy over an existing workbook.
   3. Run `rotm.py check <copy of the model folder>`. When the extract was refreshed in Google Sheets, land its export in the copy first (step 4).
4. A refresh made in Google Sheets: land the export of the refreshed extract in the copy of the model folder, with the source's new total, before you run `check`. This passage is not tested in Google Sheets; it was tested here with a local stand-in: without Google Sheets and without Excel, a copy of a built workbook whose raw rows and control cell were changed with openpyxl stood in for the download (tests `test_v4_docs.py::test_google_sheets_export_route_lands_and_checks`, `test_v5_land.py::test_export_with_more_rows_and_a_new_total_lands_and_checks`, `test_v5_land.py::test_export_with_fewer_rows_and_a_new_total_lands_and_checks` and `test_v5_land.py::test_wrong_control_is_l_total_and_writes_nothing`).
   1. In Google Sheets, before the download: ask the user for the row count and the total that the source reports for the refreshed query. The user types that total into the control input cell of the inputs sheet (the row `<t>: control total of <column>` of the block "Contract controls"), so that the workbook's own check `<t>_total_<column>` compares the raw sheet's sum with the source's new total.
   2. Make the copy of the model folder as in step 3.1.
   3. Export the refreshed extract's sheet `raw_<t>` as a CSV file (in Google Sheets, File > Download > Comma-separated values exports the current sheet; not confirmed by the research).
   4. Land the export in the copy with the source's total: `rotm.py land <copy of the model folder> --table <t> --csv <export> --force --control <t>.<column>=<source total>`. `land` checks the export against the agreed contract by the rules `check --accept-refresh` applies to refreshed rows (columns, types, nulls, keys, the row count) and against the total given. When the export fits, `land` writes `raw/<t>.csv` of the copy and records the given total for this snapshot in `raw/<t>.controls.json` with the words given (the note `recorded the source total <column> = <value> for this snapshot in raw/<t>.controls.json (given: '<text>')`). When the given total does not equal the export's sum, `land` reports L-TOTAL (exit 1) and writes nothing. The landing record, the step `land` in the copy's `reports/status.json`, names the export file (`source`) with the row count (`rows`) and the digest of the landed rows (`digest`).
   5. Download the workbook (step 1), save the download in the copy (step 3.2) and run `rotm.py check <copy of the model folder> --strict`. `check` takes the total recorded for this snapshot in `raw/<t>.controls.json`, so it needs no `--control`.
   - When the source's total did not change, leave out `--control`: `land` compares the export with the control total in force (the contract's, or the total recorded for exactly these rows in `raw/<t>.controls.json`).
   - When the download's raw sheet holds the rows of the export just landed, `check` reports no R-CHANGED. The other findings say whether the rows meet the contract and whether every check holds.
   - What a finding means when it still appears after step 5:
     - D-CONTROL-INPUT (a warning): the control input cell of the download holds another value than the total recorded: the cell was not updated in Google Sheets before the download (step 4.1). Type the total there, download again and save the download in the copy again.
     - H-COVERAGE or H-BEYOND (errors): the refresh changed the row count, and the helper rows of `h_<t>` do not end at the last raw row. Repair them in Google Sheets with step 5 of [What a refresh does to the formulas that read an extract](#what-a-refresh-does-to-the-formulas-that-read-an-extract), then download again. After that repair, `check --strict` and `audit --strict` of the copy pass (tested with the local stand-in of step 5, not in Google Sheets).
     - R-CHANGED (an error): the download's raw rows differ from the export landed in step 4.4: the export and the download come from different refreshes. Export and land again, then download again.
   - Which product calculated the saved values: the values saved in the download were calculated by Google Sheets. With Excel, `check` recalculates the download and saves Excel's values in their place (step 6). Without Excel, `check` exits 3 ("not recalculated") and reports no check value as verified.
5. Without the model folder, `rotm.py recalc <download>.xlsx --out <recalculated>.xlsx --read checks!C2` recalculates the download in Excel and saves the result as a new file, lists every error value, and reads back the cells given with `--read`. `checks!C2` is the master check of a model the plugin built (the `master_check` field of `model.manifest.json`).
6. What `check` does with the download:
   - Excel recalculates every formula of the download. The values Google Sheets computed are replaced by Excel's values in the saved file.
   - From Excel's results the plugin reads every error value (V-ERROR) and every check cell and the master check (C-FAIL when one is not 0).
   - The plugin's code, not Excel, compares each raw sheet with its contract (header names and order, R-CONTRACT; row count, keys, empty cells, types, allowed values and the control total), the helper rows with the raw rows (H-COVERAGE), and the raw sheet with the snapshot landed in `raw/<t>.csv`.
   - A raw sheet refreshed in Google Sheets differs from that snapshot unless its export was landed first (step 4), so `check` reports R-CHANGED, an error (exit 1): the download's raw sheet is a static table, and `check` accepts changed raw rows only from a Power Query table. R-CHANGED says that the rows are not the rows landed earlier; the other findings say whether the rows meet the contract and whether every check holds.
7. In the report, say which product computed which numbers: the values in Google Sheets and in the download were computed by Google Sheets; the values that `check` and `recalc` report were computed by Excel from the downloaded formulas and raw rows.
8. How Google Sheets writes a Sheets-only function into the download, and what an extract, a data source sheet or a connected pivot becomes there, is not confirmed (research synthesis D25 and section 5).

## Common mistakes

- Telling the user the model "works in Google Sheets". Say instead: it passes the plugin's cross-product rules, and it was not opened in Google Sheets.
- Typing into, or putting formulas next to or below, an extract. What a refresh does to such cells is not documented.
- Using QUERY, ARRAYFORMULA or IMPORTRANGE in a model that must also work in Excel.
- Using an open-ended range such as `raw_sales!F2:F`. It is a Google Sheets form that Excel does not read (research synthesis D5, inference, not confirmed). The skill reads whole columns (`raw_sales!$F:$F`), which researcher 2 reports work in both products (researcher 2 section 3, not confirmed).
- Landing more than 500,000 rows through an extract, or landing without comparing the row count with the contract.
- Writing analysis (rates, mappings, flags) into the BigQuery SQL. The SQL only shapes the data to the contract.
